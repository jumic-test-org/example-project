# Customer Managed KMS encryption for SQS and SNS resources

A single CMK with automatic key rotation encrypts all four messaging resources (two SQS queues, two SNS topics) in the stack. One shared key is wired to each resource via CDK's native `encryptionMasterKey` and `masterKey` properties. CDK auto-generates a key policy granting `sns.amazonaws.com` the necessary `kms:Decrypt` and `kms:GenerateDataKey` permissions, scoped by `aws:SourceArn` condition to each topic. Three new tests assert the key exists with rotation enabled, queues have a KMS key reference, and topics have a KMS key reference.

Watch for: Tests use `Match.anyValue()` which wouldn't catch a regression to AWS-managed encryption (confirmed). The key's default deletion policy is `Retain` with no explicit `removalPolicy` set, which is safe for production but worth being intentional about (confirmed).

## High-level view

The encryption uses a single shared CMK rather than per-resource keys — simpler key management, single rotation schedule, single key policy document. CDK handles the grant plumbing for SNS (the service principal needs explicit key access), and SQS consumers inherit access through IAM policies on the queue.

The test assertions verify that encryption properties exist but don't verify they reference the _specific_ CMK created in the stack. A future refactor introducing a second key (e.g., for a different compliance domain) could silently pass these tests while routing resources to the wrong key.

## Test assertions don't pin encryption to the stack's CMK

The three new tests check `KmsMasterKeyId: Match.anyValue()`. This verifies that _some_ key is configured, but not that it's the `ExampleProjectKey` created in this stack. The synthesized template shows the queues reference the key via `Fn::GetAtt: [ExampleProjectKeyD757E2D5, Arn]`. A stronger assertion would match against a `Ref` or `Fn::GetAtt` pointing to the key's logical ID:

```typescript
template.hasResourceProperties('AWS::SQS::Queue', {
  KmsMasterKeyId: {
    'Fn::GetAtt': [Match.stringLikeRegexp('ExampleProjectKey'), 'Arn'],
  },
});
```

A refactor that accidentally assigns a different key (or falls back to AWS-managed SSE-KMS via `encryption: QueueEncryption.KMS_MANAGED`) would still pass the current tests.

## KMS Key lifecycle and deletion behavior

The synthesized key has `UpdateReplacePolicy: Retain` and `DeletionPolicy: Retain` (CDK's default for KMS keys), with no explicit `removalPolicy` in the construct props. For development/test stacks that get torn down frequently, this accumulates orphaned keys in the account. Documenting the intent with an explicit property avoids ambiguity about whether `Retain` is deliberate or accidental.
