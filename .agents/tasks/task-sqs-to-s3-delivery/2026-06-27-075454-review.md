# SQS-to-S3 message delivery via Lambda

This change adds infrastructure to persist messages arriving on `ExampleProjectQueue1` into an S3 bucket. A Lambda function is triggered by an SQS event source mapping, reads each record's body, and writes it to S3 under a `messages/{timestamp}_{messageId}.json` key. The bucket uses the project's existing KMS key for encryption. cdk-nag compliance is handled through a mix of the standard `Validations.of().acknowledge()` API and direct metadata injection to work around a CDK bug with bracketed finding IDs.

**Watch for:** The Lambda processes SQS records sequentially with no error isolation — a single S3 write failure fails the entire batch and returns all messages to the queue (confirmed). The S3 key uses wall-clock time (`new Date()`) rather than the SQS message timestamp, so key ordering doesn't reflect actual message arrival order, and retried messages get new keys, producing duplicates (confirmed). `grantWrite` includes `s3:DeleteObject*` which is broader than necessary for an append-only message store (confirmed).

## High-level view

The delivery pipeline is straightforward: SQS event source mapping triggers Lambda, Lambda iterates records and PUTs each to S3. There's no batching optimization, no dead-letter configuration on the event source mapping itself, and no partial-batch failure reporting — which means one poisonous message can block processing of the entire queue until it expires from the source queue's redrive policy (if any).

The cdk-nag acknowledgement strategy splits into two paths: standard `acknowledge()` calls for simple rule IDs, and raw metadata injection for IDs containing `::` that the CDK API rejects. This workaround is brittle against future cdk-nag ID format changes — a major version bump could silently invalidate the acknowledgements.

The test suite verifies resource existence and configuration but doesn't assert IAM policy statements or the Lambda's log group association.

<summary>Issues (5)</summary>

1. **No partial-batch failure reporting** — The Lambda doesn't return `batchItemFailures`, so any single record failure causes the entire batch to return to the queue. Set `reportBatchItemFailures: true` on the event source and return failed message IDs from the handler.
2. **Sequential writes without error isolation** — A `PutObjectCommand` failure for one record aborts processing of subsequent records in the same batch. Wrap each write in try/catch and collect failures for partial-batch reporting.
3. **Wall-clock timestamp in S3 keys** — Using `new Date()` instead of the SQS `attributes.SentTimestamp` means retries produce duplicate objects under different keys, and key ordering doesn't reflect actual send order. Use the message's own timestamp for deterministic keys.
4. **grantWrite is overly broad** — `bucket.grantWrite()` includes `s3:DeleteObject*` and `s3:Abort*`. For an append-only store, `grantPut()` would be least-privilege.
5. **No IAM policy assertions in tests** — Tests verify resource existence but don't assert that the Lambda's execution role has the expected S3/KMS/SQS permissions, which is where permission regressions typically hide.

## Batch failure semantics and message retry behavior

The Lambda handler iterates `event.Records` and awaits each `PutObjectCommand` sequentially. If the third record in a batch of ten fails, records 4-10 are never processed, and the entire batch returns to SQS for retry (including records 1-2 which were already successfully written to S3). This produces duplicate writes for the successful records on retry.

The SQS event source mapping supports `reportBatchItemFailures` (set via the `reportBatchItemFailures` property on `SqsEventSource`). With this enabled, the handler can return `{ batchItemFailures: [{ itemIdentifier: messageId }] }` to tell SQS which specific messages failed, allowing successful messages to be deleted from the queue while only failures retry. Without it, the blast radius of a single bad message is the entire batch.

In production, a single malformed message or transient S3 error would cause repeated reprocessing of the entire batch until the message ages out of the queue.

## S3 key design and idempotency

```javascript
const timestamp = new Date().toISOString().replace(/[:.]/g, '-');
const key = `messages/${timestamp}_${messageId}.json`;
```

The key incorporates wall-clock time at the moment of Lambda execution rather than the message's inherent timestamp (`record.attributes.SentTimestamp` or `record.attributes.ApproximateFirstReceiveTimestamp`). The same message processed twice (due to SQS at-least-once delivery or the batch failure issue above) produces two distinct S3 objects because the timestamp differs on each invocation. If idempotency is desired, the key should be derived solely from the `messageId` — e.g., `messages/{messageId}.json` — so repeated processing overwrites the same object.

Using wall-clock time also means objects are ordered by processing time rather than send time. Under load or during retries, this ordering diverges from the actual message sequence.

## IAM permission scope

The implementation uses `messageBucket.grantWrite(sqsToS3Function)`, which grants `s3:PutObject`, `s3:Abort*`, and `s3:DeleteObject*`. For a message persistence use case that only ever writes objects, `grantPut()` (which grants only `s3:PutObject`) would follow least-privilege more closely. The broader grant means the Lambda could delete objects from the bucket — an unnecessary capability that expands the blast radius of a compromised function.

## cdk-nag workaround fragility

The direct metadata injection bypasses the standard `Validations.of().acknowledge()` API because that API rejects finding IDs containing `::`. The workaround functions correctly today, but if cdk-nag changes its metadata key name or lookup behavior in a major version bump, these acknowledgements silently stop working and the nag check starts failing. A comment documenting the CDK issue number would help future maintainers understand why this pattern exists.

## Test coverage gaps

Not tested: IAM policy statements on the Lambda execution role (the actual permissions granted by `grantWrite`, `grantConsumeMessages`, and `grantEncryptDecrypt`). Not tested: the log group association with the Lambda. Not tested: the bucket's `BlockPublicAccess` and `enforceSSL` configuration. Any of these could regress silently under CDK version upgrades without test coverage.
