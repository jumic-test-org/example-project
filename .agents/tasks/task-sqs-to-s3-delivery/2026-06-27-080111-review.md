# SQS-to-S3 message delivery via Lambda (v2)

This change adds infrastructure to persist messages arriving on `ExampleProjectQueue1` into an S3 bucket. A Lambda function triggered by an SQS event source mapping iterates each record, writes the body to S3 under a `messages/{sentTimestamp}_{messageId}.json` key, and returns partial-batch failure reports for any records that fail. The bucket uses the project's existing KMS key for encryption, and permissions follow least-privilege with `grantPut()` instead of `grantWrite()`. All five v1 review issues have been addressed.

**Watch for:** The S3 key still includes `messageId` alongside `SentTimestamp`, which makes retried messages (SQS at-least-once delivery) produce duplicate objects rather than overwriting — acceptable for an append-only store but worth noting if deduplication is ever required (likely). The cdk-nag metadata workaround for bracketed finding IDs lacks a reference to the upstream CDK issue, making it opaque to future maintainers (confirmed).

**Verdict**: APPROVED

## High-level view

The delivery pipeline now handles partial failures gracefully: each record is processed independently inside a try/catch, failures are collected and returned as `batchItemFailures`, and the event source mapping declares `reportBatchItemFailures: true`. A single poisonous message no longer blocks the entire batch.

The permission model uses `grantPut()` (only `s3:PutObject` and `s3:Abort*`), and the negative test asserting no `s3:DeleteObject*` guards against regression.

The cdk-nag acknowledgement workaround using direct metadata injection is documented with a code comment explaining the `::` rejection issue, but adding the upstream CDK issue link would complete the breadcrumb trail for future removal.

<summary>Issues (2)</summary>

1. **Duplicate objects on SQS retry** — The S3 key includes both `SentTimestamp` and `messageId`, so the same message retried (at-least-once delivery) produces a second object since `messageId` changes per delivery attempt. If deduplication matters in the future, the key should use only the original message ID from the message body or attributes. Low priority for an append-only store.
2. **Missing upstream issue reference in cdk-nag workaround** — The code comment explains _what_ the workaround does but not _where_ to track the upstream fix. Adding the CDK GitHub issue link would help maintainers know when the workaround can be removed.

## At-least-once delivery and key uniqueness

The S3 key is `messages/${timestamp}_${messageId}.json` where `timestamp` derives from `SentTimestamp` and `messageId` is the SQS message ID. SQS guarantees that `messageId` is unique per delivery attempt, not per logical message. Standard queues can deliver the same logical message multiple times with different `messageId` values. Each delivery produces a distinct S3 object. For an append-only message store this is a minor data amplification issue rather than a correctness bug — no data is lost, but storage grows on retries. If the queue were FIFO (with deduplication IDs), this wouldn't apply, but the current queue is standard.
